# W3 — inspeção histórica no perfil Dev autenticado e HTTP 403 observado

Data: 20/10/2026. Produto: OrdaX Orchestrator Lab. PR: #268.

## Ambiente verificado

A instância Dev original (fontes de 19/10) foi encontrada em execução no Windows e, pelo launcher oficial `start-lab.mjs --staged`, vinculada ao perfil de desenvolvimento separado do aplicativo instalado. A consulta às funções oficiais do App confirmou `session_present`, compositor disponível, 7 tarefas e 5 conversas vinculadas. O SQLite correto confirmou `quick_check=ok`, 7 tarefas, 5 links, 4 Runs concluídas, 3 falhas e 1 interrupção antiga. **0 Runs em andamento** e **0 eventos `provider.submission.provenance` históricos**.

Não havia rascunho local visível. Um backup local do SQLite foi gerado pela API oficial `node:sqlite.backup`, verificado com `quick_check`, e uma cópia isolada foi aberta pelo Store da fonte canônica de 20/10, preservando exatamente as sete tarefas e cinco conversas. O backup permanece somente no computador autorizado, fora do GitHub; nenhum cookie, token ou perfil de navegador foi duplicado.

A janela Dev antiga recebeu fechamento normal. O fechamento levou mais que a primeira janela de observação, mas terminou naturalmente, sem `taskkill` ou `Stop-Process -Force`. Em seguida o Electron canônico da branch W3 foi aberto com a vinculação staged existente e contrato `--ordax-lab-staged-approved`/`--remote-debugging-port=9446`. O gate oficial `waitForLabAppMode` confirmou a interface OrdaX e o fingerprint do **mesmo** perfil. A sessão reapareceu como `session_present`; as 7 tarefas e os 5 links continuaram no App. Nenhuma Run nova foi criada.

## Uma única inspeção real de W3

A inspeção ocorreu **no modo do OrdaX App**, pelo botão canônico `Verificar conversa`, usando uma das duas tarefas históricas elegíveis encontradas no SQLite. O teste foi somente leitura e não fez envio:

```json
{

  "appMode": true,

  "providerMessagesSent": 0,

  "observationKind": "unavailable",
  "observationReason": "thread_dom_not_ready",
  "threadRendered": false,
  "inconclusive": true

```

**Não houve nova tentativa de navegação.** Uma verificação subsequente de saúde do próprio OrdaX confirmou `pageType=conversation`, `authState=unknown`, `composerReady=false` e **9 respostas HTTP 403** de recursos do backend do ChatGPT observadas no navegador. Esses códigos são fatos observados, **não demonstram qual endpoint falhou nem provam a causa do DOM ausente**. A prova W3 permanece inconclusiva. A existência de zero recibos históricos também impede certificação retroativa do prompt conforme o contrato atual.

## Correção no diagnóstico canônico

`src/provider-historical-thread-preflight.mjs` passou a exportar `classifyHistoricalThreadPostNavigation`: somente após `thread_dom_not_ready`, e somente quando um sinal pós-navegação de backend 403/429 é explicitamente observado, retorna respectivamente `provider_access_restricted_observed` ou `provider_rate_limited_observed`. Ausência de DOM ou saúde desconhecida isoladamente não produzem inferência.

`desktop/embedded-worker.mjs` reutiliza `this.health()` **uma única vez** após o observer read-only já concluído. Não há segunda navegação, reobservação do DOM, submit, autenticação automática, reload ou bypass. `desktop/ui.js` comunica o sinal HTTP como observado, sem afirmar que não ocorreu a navegação autorizada inicial. Os testes de contrato validam os casos 403, 429, desconhecido, DOM válido, outras falhas e chamada única do worker.

**Limites:** a nova correção precisa de inicialização futura do App para estar ativa no Electron; não foi repetido o teste real após a observação dos 403. W3 e W4 reais não estão certificados. A PR continua em rascunho; sem merge à main, sem release, sem alteração de OS/USB, sem envio de mensagens ao ChatGPT.
